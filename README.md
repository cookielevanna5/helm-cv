# Shop Platform Helm Chart

Reusable Helm chart for deploying multiple application components that share a common deployment structure while allowing per-component and per-instance customization.

The chart is designed for environments such as:

- Development
- Preproduction
- Production

and supports:

- Multiple application components
- Shared global configuration
- Per-component shared configuration
- Per-instance deployment variations
- Dynamic ConfigMap generation
- Shared deployment templates
- Resource inheritance and overrides

---

# Architecture

The chart hierarchy is:

```text
Global
   ↓
Component
   ↓
Instance
```

Configuration inheritance:

```text
Global values
    ↓
Component values
    ↓
Instance values
```

Example:

```text
orders
├── image: ghcr.io/acme/orders-service:1.3.0
├── replicas: 5
├── resources
├── commonConfig
└── instances
      ├── eu
      ├── us
      └── asia
```

This generates:

```text
Deployment/orders-eu
ConfigMap/orders-eu-config

Deployment/orders-us
ConfigMap/orders-us-config

Deployment/orders-asia
ConfigMap/orders-asia-config
```

# Global Configuration

Global values apply to every deployment generated by the chart.

Example:

```yaml
global:
  annotations:
    prometheus.io/scrape: "true"

  labels:
    team: backend
    environment: prod

  imagePullSecrets:
    - name: prod-regcred

  resources:
    requests:
      cpu: 100m
      memory: 128Mi

    limits:
      cpu: 500m
      memory: 512Mi
```

Available global properties:

| Property         |                           Purpose |
| ---------------- | --------------------------------: |
| annotations      | Shared pod/deployment annotations |
| labels           |                     Shared labels |
| imagePullSecrets |              Registry credentials |
| resources        |           Default resource values |
| nodeSelector     |                    Pod scheduling |
| tolerations      |                    Pod scheduling |
| affinity         |                    Pod scheduling |

# Adding a New Component

Example:

Suppose we want a new service:

```text
inventory
```

Add:

```yaml
components:
  - componentName: inventory

    image: ghcr.io/acme/inventory-service:1.0.0

    replicas: 2

    commonConfig:
      DB_PORT: "5432"
      LOG_LEVEL: info

    instances:
      - name: default
        config:
          DB_HOST: inventory-db
```

Generated resources:

```text
Deployment/inventory-default

ConfigMap/inventory-default-config
```

No template changes are required.

# Adding Multiple Deployment Instances

Suppose a component needs multiple deployments:

```yaml
components:
  - componentName: orders

    image: ghcr.io/acme/orders-service:1.3.0

    replicas: 5

    commonConfig:
      DB_PORT: "5432"

    instances:
      - name: eu
        config:
          DB_HOST: postgres-eu
          REGION: eu

      - name: us
        config:
          DB_HOST: postgres-us
          REGION: us

      - name: asia
        config:
          DB_HOST: postgres-asia
          REGION: asia
```

Generated:

```text
Deployment/orders-eu
Deployment/orders-us
Deployment/orders-asia
```

# ConfigMap Behavior

ConfigMaps combine:

1. Component shared config
2. Instance-specific config

Example:

Input:

```yaml
commonConfig:
  DB_PORT: "5432"
  LOG_LEVEL: warn

instances:
  - name: eu
    config:
      DB_HOST: postgres-eu
      REGION: eu
```

Generated:

```yaml
data:
  DB_PORT: "5432"
  LOG_LEVEL: "warn"

  DB_HOST: "postgres-eu"
  REGION: "eu"
```

# Resource Configuration

Resources inherit from:

```text
Global resources
    ↓
Component resources override global
```

## Default resources

```yaml
global:
  resources:
    requests:
      cpu: 100m
      memory: 128Mi

    limits:
      cpu: 500m
      memory: 512Mi
```

Every component uses this unless overridden.

---

## Override resources for one component

Example:

```yaml
components:
  - componentName: orders

    resources:
      requests:
        cpu: 1
        memory: 1Gi

      limits:
        cpu: 4
        memory: 4Gi
```

Only orders receives larger resources.

---

# Resource Guidelines

Recommended starting values:

Small services:

```yaml
requests:
  cpu: 100m
  memory: 128Mi

limits:
  cpu: 500m
  memory: 512Mi
```

Medium services:

```yaml
requests:
  cpu: 500m
  memory: 512Mi

limits:
  cpu: 2
  memory: 2Gi
```

Heavy workloads:

```yaml
requests:
  cpu: 1
  memory: 1Gi

limits:
  cpu: 4
  memory: 4Gi
```

Avoid:

❌ requests > limits

Bad:

```yaml
requests:
  cpu: 2

limits:
  cpu: 1
```

Correct:

```yaml
requests:
  cpu: 1

limits:
  cpu: 2
```

# Customization Examples

Add labels:

```yaml
global:
  labels:
    owner: team-a
    application: shop
```

Add annotations:

```yaml
global:
  annotations:
    sidecar.istio.io/inject: "true"
```

Add registry credentials:

```yaml
global:
  imagePullSecrets:
    - name: my-registry-secret
```

Add scheduling constraints:

```yaml
global:
  nodeSelector:
    workload: backend

  tolerations:
    - key: dedicated
      operator: Equal
      value: backend
      effect: NoSchedule
```

# Best Practices

✓ Keep environment differences in values files only

✓ Put shared values under global

✓ Put shared component values under component level

✓ Keep instance values minimal

✓ Avoid duplicate images/resources

✓ Preview changes using:

```bash
helm template
```

before deployment
